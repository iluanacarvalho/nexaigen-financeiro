## Architecture

This is NEXAIGEN's own internal billing/collections tool — it is never sold to or accessed by municipalities, and its database must never be shared with `nexaigen-educa` (that repo is multi-tenant across prefeituras; this one is mono-tenant, scoped to NEXAIGEN's own team). Purpose: track invoices sent to each contracted prefeitura through to payment, with minimal manual work as the client count grows.

**ACHADO CRÍTICO DE SEGURANÇA (corrigido) — este projeto não tinha login nenhum até uma rodada anterior.** `usuario_interno` (schema original) was meant to gate access via Supabase Auth + RLS, but was never wired to any real sign-in flow — confirmed by a full-repo grep before removing it: zero references outside the schema file itself. Every API route (`/api/clientes`, `/api/notas`, `/api/notas/[id]/verificar`, `/api/alertas`) and every page (`/`, `/clientes`, `/alertas`, `/checagem`) was completely open to anyone with the URL — no session check anywhere. Replaced by a real login (`lib/auth.ts`): bcrypt + JWT (`jose`), backed by `equipe_nexaigen`/`sessao` (see `db/migrations/0001_initial.sql`, Section 1). Since round 15-A there ARE roles (see "Team roles / RBAC" below) — only admins create teammates (`POST /api/equipe`, papel required). `usuario_interno` itself was dropped for good (never carried over to the Postgres-direct schema below).

**Every route now calls `exigirPapel(await obterContextoAutenticado(token), area)` first** (`lib/auth.ts`; it runs `exigirSessao` and then the role check — round 15-A) — `obterContextoAutenticado` takes the token as an explicit parameter (never reads `next/headers#cookies()` itself), deliberately mirroring `nexaigen-educa`'s `lib/auth.ts` contract even though this project's proxy.ts (round 15-B) only sets /mapa headers, never auth: this is what makes the function trivially unit-testable (pass a string, mock `@/lib/db`) instead of crashing outside a real Next.js request scope. `exigirSessao()` ALSO blocks with 403 when `precisaTrocarSenha` is true — centralized there (not per-route, not only in the `/trocar-senha` page) since this project has no middleware layer to put that check in, and every current caller of `exigirSessao()` is a route that should be blocked by it. `/api/auth/**` never calls `exigirSessao()` (needs to work before/to get out of that state). Pages: `app/(protegido)/layout.tsx` is the page-level equivalent (Server Component, redirects to `/login` — or `/trocar-senha` if a temp password is still pending), wrapping `/`, `/clientes`, `/alertas`, `/checagem`, `/equipe` (a route group — doesn't affect the URL). `/login` and `/trocar-senha` live outside that group on purpose (can't require a session that doesn't exist yet / must render even mid-forced-password-change).

**INFRASTRUCTURE MIGRATION — Supabase → Postgres direct via "pg" (`lib/db.ts`), pedido explícito da Luana: mesma arquitetura do `nexaigen-educa`, sem depender de um projeto Supabase configurado à parte** (that's exactly what blocked the first real login for a whole round — an old, forgotten Supabase project whose URL was never even filled into `.env.local`). Pool cached on `globalThis`, `query<T>(sql, params, executor?)`, `withTransaction(fn)` — identical contract to `nexaigen-educa/lib/db.ts`. Three type parsers preserve the exact response shape the Supabase client used to produce (see the long comment block at the top of `lib/db.ts` for the evidence behind each): `bigint`/`int8` (oid 20, only `token_version`) → `Number(...)` (the pg driver returns int8 as a string by default — comparing that against the JWT's numeric claim would have silently broken every login); `date` (oid 1082) → returned as the raw wire string, unparsed (the pg driver's default `Date`-object behavior would have turned `data_emissao` from `"2026-08-01"` into a full ISO datetime, visibly changing text interpolated directly into `app/(protegido)/checagem`); `timestamptz` (oid 1184) → `new Date(v).toISOString()`, same as `nexaigen-educa`. `numeric` needed **no** parser — the pg driver already returns it as a string by default, exactly like Supabase did (confirmed by the frontend already wrapping every money field in `Number(...)`). No RLS/policies in the new schema — that's a Supabase-specific concept (anon vs. service_role key at the PostgREST edge); a Postgres reached only via the app's own `DATABASE_URL` has no less-privileged key to protect against, so recreating RLS-shaped policies here would be security theater. `lib/supabase/` (both files) was deleted outright, along with the now-unused `@supabase/supabase-js` dependency.

**`app/(protegido)/alertas/page.tsx` used to self-fetch its own `/api/alertas` from a Server Component** (`fetch(`${base}/api/alertas`)`) — broke the moment that route started requiring a session, since a Server Component's self-fetch to an absolute URL never forwards the incoming request's cookies automatically. Fixed by querying the database directly instead (same pattern the dashboard page already used) rather than trying to thread the cookie header through — avoids the problem instead of working around it. Both pages share the same 3-table `json_build_object` query as `GET /api/alertas` (see that route for the full reasoning on reproducing Supabase's nested embed shape in plain SQL).

**`POST /api/notas/[id]/verificar`'s `verificado_por` used to come from the request body** (`z.string().uuid().optional()`), never checked against who actually called it — anyone could claim to be someone else. Now always derived from `contexto.equipeId` (the real session), never accepted from the client — same principle already applied throughout `nexaigen-educa`'s admin routes (never trust client-supplied identity when a real session exists to derive it from).

**The whole domain reduces to one pure function.** `lib/prazos.ts#diagnosticarNota()` takes a nota's current state (has it been atested? when? has it been paid?) plus "now", and returns both a derived status and, optionally, which alert to raise. It has no I/O and isn't aware of the database — this is deliberate, since it's the one piece of business logic worth unit-testing in isolation (`lib/prazos.test.ts`). If the escalation rules change, change the thresholds/logic here first, then trace outward to the cron job.

**Legal deadline is computed in the database, not just in application code.** `nota_fiscal.data_limite_pagamento` is set by a Postgres trigger (`trg_calcular_data_limite`) the moment `data_atesto` is written — `data_atesto + 30 days` (Lei 14.133/2021, Art. 141). This means the deadline can't be wrong even if a future code path writes `data_atesto` without going through the "official" update flow.

**`app/api/cron/verificar-prazos` is the only place that mutates alert/status state in bulk — and it's the ONE route in this project that never calls `exigirSessao()`, by design.** It runs once a day via **GitHub Actions** (`.github/workflows/verificar-prazos.yml`, 09:00 UTC + manual dispatch; hosting is Railway — the old `vercel.json` cron was removed in round 07 because it never fires outside Vercel), **POST only**, authenticated by `lib/segredoCompartilhado.ts#bearerConfere` (sha256 digests compared with `crypto.timingSafeEqual` — constant time and no length leak). It returns a summary (`notasAvaliadas`, `statusAtualizados`, `alertasCriados`, `emails.{enviados,falhos,semDestinatario}`, `contadoresRateLimitRemovidos`) that the workflow prints. **Deploy: the repo needs secrets `FINANCEIRO_URL` (public URL, no trailing slash) and `CRON_SECRET` (same value as on Railway)** — without them the workflow warns and exits 0. A scheduler has no way to log in as a teammate, so this route is deliberately outside the equipe_nexaigen session system entirely — `app/api/protecao-rotas.test.ts` asserts this explicitly (CRON_SECRET alone is sufficient, no session ever required). It scans every open nota, re-derives status via `diagnosticarNota()`, and inserts alerts with `insert ... on conflict (nota_fiscal_id, tipo) where status <> 'resolvido' do nothing returning id` — the partial unique index `uq_alerta_ativo` in `db/migrations/0001_initial.sql` (one active alert per nota+tipo) is what actually guarantees idempotency; the `on conflict` clause (Supabase's `upsert`+`ignoreDuplicates` before the infrastructure migration, same effect) is a secondary guard, not the source of truth. Don't add a second code path that also writes `alerta_cobranca` without going through the same insert pattern.

**Notification is a single channel by design**: `lib/notificacao-interna.ts` sends email via Resend (`RESEND_API_KEY`) when an `atraso_60_dias` alert fires — the internal alert to NEXAIGEN's own collections team (`COBRANCA_EMAIL_DESTINO`). It fails soft — if `RESEND_API_KEY` or `COBRANCA_EMAIL_DESTINO` is unset, it logs a warning and returns rather than throwing, so a missing env var never breaks the cron run. That also means a misconfigured environment sends zero notifications with no loud failure — check the Railway server logs (and the summary printed by the verificar-prazos workflow), not just "did the job run". Body is HTML now (`lib/emailTemplate.ts#montarEmailHtml`, NEXAIGEN navy/teal identity — same visual identity as nexaigen-educa, deliberately, same company).

**`lib/notificacaoCliente.ts` — the client-facing counterpart, added in the "e-mails bonitos e cobrança automática" round.** Sends an email to the debtor prefeitura's own contact (`cliente_prefeitura.contato_email`, already existed in the schema) for all 4 `TipoAlerta` stages, not just `atraso_60_dias`. **Tone is the whole point of this feature**: copy escalates from neutral/helpful (`sem_atesto_prolongado`) to more serious-but-still-cordial (`atraso_60_dias`) — no stage ever contains a legal threat or affirmation ("vamos protestar", "medidas legais", etc.), since this goes out automatically, in the company's name, to an institutional client. Every client email is BCC'd (never a visible CC) to `COBRANCA_EMAIL_DESTINO` so the collections team has full visibility of what goes out automatically. **Fires only on state transition, never once per day while the state persists** — deliberately reuses `alerta_cobranca`'s existing `uq_alerta_ativo` partial unique index + the cron route's `on conflict ... do nothing returning id` insert (a row is only returned when actually newly inserted) instead of adding a new tracking column — see the comment at the top of `lib/notificacaoCliente.ts` and in `app/api/cron/verificar-prazos/route.ts` for why that's sufficient.

**No portal credentials are ever stored.** `cliente_prefeitura.portal_usuario` is a login *name* only; there is deliberately no password column. Checking whether a prefeitura's portal shows a nota as atestada is a manual step (`app/checagem`) by design — see `README.md` for the reasoning and staffing math behind that choice. Don't add a password/secret field to this table without revisiting that decision explicitly.

**PDF da nota fiscal — upload/download, `lib/armazenamentoObjetos.ts` REAPROVEITADO tal e qual do projeto irmão `nexaigen-educa`, pedido explícito da Luana (mesmo padrão de storage, não um segundo módulo).** Este projeto não emite NF-e — a nota já é emitida fora (prefeitura/contador), aqui só se guarda o arquivo. `nota_fiscal.arquivo_pdf_chave`/`arquivo_pdf_nome` (`0002_nota_fiscal_arquivo_pdf.sql`, ambos nulos até o primeiro anexo) guardam só os metadados; o arquivo em si vai pro Railway Buckets (S3-compatível, privado — toda leitura passa pelo servidor em streaming desde a rodada 08, nunca uma URL direta). `POST /api/notas/[id]/arquivo` exige sessão, valida Content-Type `application/pdf`, tamanho até 10MB, E a **assinatura real do arquivo** (`%PDF-` nos 5 primeiros bytes) — mais rigoroso que o precedente de prestação de contas de convênio em `nexaigen-educa` (que só confere Content-Type + extensão do nome), porque aqui a validação foi pedida explicitamente. **Since round 06, every upload is a new row in `nota_fiscal_arquivo_versao` (`0005_nota_fiscal_arquivo_versao.sql`, backfills v1 for legacy notas) — never delete a version or its bucket object in any flow**: key `financeiro/notas-fiscais/{notaId}/versoes/{uuid}/{nome}` (unique per upload), sha256/size/`enviado_por`/`motivo` stored, next version computed inside a transaction that locks the nota row (`for update`) and also moves `arquivo_pdf_chave`/`arquivo_pdf_nome` (still the "current version" pointer). Bucket failure → nothing written; DB failure after upload → `removerUploadNaoRegistrado` (the ONLY bucket delete in the project) + `alertarErroSistema("nota_fiscal_pdf")` if that cleanup fails. `GET /api/notas/[id]/arquivo[?versao=N]` streams the bytes through the server (Content-Disposition sanitized, `no-store`) instead of a presigned URL; `GET .../arquivo/versoes` lists history. UI em `app/(protegido)/checagem/page.tsx` (única tela que já lista notas individualmente nesta rodada — não existe ainda uma listagem geral de TODAS as notas fiscais, então o anexo só é alcançável pela UI enquanto a nota está `aguardando_atesto`; ver pendência no README.md).

**Integração nexaigen-educa → Financeiro — `POST /api/integracao/clientes` (`0004_integracao_educa.sql`).** The Educa, after provisioning a município, creates/updates the matching `cliente_prefeitura` here. Bancos continuam separados. Authenticated ONLY by `INTEGRACAO_SECRET` (Bearer, `timingSafeEqual` — same pattern as `CRON_SECRET`; same value as `INTEGRACAO_FINANCEIRO_SECRET` on the Educa side), never by session — the second route (after the cron) that never calls `exigirSessao()`, asserted in `app/api/protecao-rotas.test.ts`. Missing secret on the server → 401 + `alertarErroSistema("integracao_educa", ...)`; wrong secret → plain 401, no alert. Idempotent via `municipio_id_externo` (Educa's município uuid, no FK) + partial unique index `uq_cliente_municipio_id_externo`: single `insert ... on conflict (municipio_id_externo) where municipio_id_externo is not null do update` (predicate must match the index exactly), `(xmax = 0) as criado`; on UPDATE, absent optional fields keep their stored value (coalesce). Contract PDF arrives base64 in the JSON — invalid → 400; bucket upload failure → client still saved without contract + `avisoContrato`. Team-side equivalents: `GET`/`PATCH /api/clientes/[id]` (PATCH `.strict()`: can't touch `municipio_id_externo`/`contrato_arquivo_*`), `POST`/`GET /api/clientes/[id]/contrato`. Key prefix `financeiro/contratos-prefeitura/`. PDF rules (size/type/`%PDF-`) shared in `lib/validacaoPdf.ts`; zod schema shared in `lib/clienteSchema.ts` (route.ts files can't export arbitrary names).

**Painel financeiro (`/painel`, `GET /api/painel-financeiro`, `?formato=csv`)** — all math is pure in `lib/painelFinanceiro.ts` (integer cents via `paraCentavos`, never float; "hoje" in America/Sao_Paulo passed as a parameter; open-nota status re-derived with `diagnosticarNota` at today's date instead of the cron-written column; KPI without a base is `null`/"—", never a fake 0), read by 2 fixed queries in `lib/painelFinanceiroRepositorio.ts` (no N+1, no contact fields read); `vitest.integration.config.ts` now loads `.env.local` then `.env` itself.

**Round 07 — rate limit, atomic alert debounce, config status, test isolation.** `lib/rateLimit.ts` + `rate_limit_contador` (`0006_rate_limit.sql`): fixed-window counters, `insert ... on conflict do update ... returning` (increment-and-read in one statement; increment FIRST, then decide; `desfazerTentativa`/`zerarContador` when the attempt succeeds so only failures accumulate; keys are `prefix:sha256(identifier)`, never raw e-mail/IP; old windows purged by the daily cron). Applied: login 5 failures/15 min per normalized e-mail AND per IP (`x-forwarded-for` first value → 429 + Retry-After; success zeroes the e-mail counter; non-existent e-mail runs bcrypt against `HASH_FANTASMA` so timing doesn't leak existence), trocar-senha 10/15 min per account, integração 60/min per IP + 10 auth failures/15 min per IP. `lib/alertaErroSistema.ts` debounce is now truly atomic via a per-category PK row in `alerta_sistema_debounce` (`0007`) — the old single `insert ... where not exists` was NOT race-free (measured 4–10 rows for 20 concurrent calls). `lib/statusConfiguracao.ts` + `GET /api/configuracao/status` + Dashboard banner expose booleans only, never values. `vitest.setup.sem-apis-externas.ts` (both suites) deletes Resend/bucket credentials and blocks non-localhost `fetch`. CI (`ci.yml`) runs typecheck → lint → test → migrate → test:integration → build against a `postgres:16` service.

**Round 08 — Notas fiscais screen, one source of numbers, versioned contract, streaming, component tests.**
- **State machine** `lib/estadoNota.ts` (pure): `situacaoDaNota` (situation at today's date — the ONE derivation used by Painel, Dashboard, `/notas`, cron via `statusPersistidoDe`), `validarTransicao`/`acoesPermitidas` (payment only after atesto; cancel only open notes; reopen only paid), input validators (value as TEXT → cents, competência → 1st of month). `lib/notasServico.ts` applies it in transactions with `select ... for update` on the nota; every action writes `nota_fiscal_evento` (`0008`, with author). Listing filters by situation in SQL (`SQL_SITUACAO`) — must stay equivalent to `situacaoDaNota`; `lib/notasServico.integration.test.ts` checks it at the 0/1/59/60-day borders. `/verificar` delegates to the same service.
- **Numbers**: Dashboard reads `lib/resumoDashboard.ts` (→ `obterPainelFinanceiro`); never sum `Number(valor)` again — money helpers live in `lib/dinheiro.ts`.
- **PDF versioning** for BOTH nota and contract is `lib/versionamentoPdf.ts` (`ALVO_PDF_NOTA`, `ALVO_CONTRATO`; `0009` backfills contract v1); the Educa integration creates a contract version (`enviado_por` null). Downloads stream via `abrirLeituraArquivo` (`ausente` → 404, `indisponivel` → 502). `npm run recalcular-hash-versoes` fills legacy sha256/size.
- **Tests**: `npm run test:component` (jsdom, `*.component.test.tsx`, no jest-dom — it breaks `npm install` on npm 10); `testes/bucketEmMemoria.ts` and `testes/fetchFalso.ts` are test-only helpers.

**Dependencies & security (rounds 09-A, 13-A).** Next.js is pinned at **16.4.6** (exact; `eslint-config-next` same version). Since 16.4.5 the Next server DROPS `content-length`/`content-encoding`/`transfer-encoding` from route handler Responses (GHSA-pc58-hwjq-p385, `next/dist/server/send-response.js`) — PDF downloads stream chunked and rely on Next destroying the socket on a mid-stream bucket error; `lib/downloadPdfNoServidorNext.test.ts` runs the real `sendResponse` to pin that (re-run it on every Next upgrade). 16.4.6 also compresses route handler responses on self-hosted `next start`. Policy: apply Next.js security patches within 7 days. CI runs `npm audit --omit=dev --audit-level=high` as a **blocking** step (prod deps only) plus a full informative `npm audit`. Regenerate the lock ONLY with **npm 10.9** (`npx npm@10.9 install ...`) and validate with `rm -rf node_modules && npm ci`. `package.json#overrides.vitest` must stay equal to `devDependencies.vitest` — it breaks an optional-peer cycle (`vite → @vitejs/devtools → devtools-vitest → vitest@*`) that crashes npm 10.9's resolver. `images.unoptimized: true` in `next.config.js` on purpose (no `next/image`/`next/og` in this app; `/_next/image` → 404, removing the attack surface of recent image-optimizer advisories) — don't add `next/image` without revisiting it.

**Zod 4 (round 10-A).** Use the v4 APIs only: `z.strictObject` (not `.strict()`), `z.uuid()/z.email()/z.url()` (not `z.string().uuid()` etc.), `{ error: "..." }` (not `message`). Every 400 builds `detalhes` with `lib/validacao.ts#detalhesDoErro` (same `{formErrors, fieldErrors}` shape as v3 `.flatten()` — API contract) and route ids are checked with `ehUuid`. **Never put `.default()` on a field that is reused by an optional/partial schema** — in v4 defaults inside optional fields ARE applied (see `lib/clienteSchema.ts`: defaults live only in the create schema). `app/api/contrato-validacao.test.ts` pins the 400 contract of every validated route.

**Plans by municipality size (round 11-A).** `lib/planos.ts` is the single source (ids `dispensa`, `pequeno_porte`, `medio_porte`, `grande_porte`; default monthly fee and implementation fee in integer cents). **A plan never gates features — only price.** Stored values (`valor_mensal`, `taxa_implantacao`) are the negotiated ones: defaults apply only on CREATE (`ClienteSchema` transform; PATCH and the Educa upsert never re-apply them). Money in client schemas is TEXT → cents (`lerValorMonetario`, now in `lib/dinheiro.ts`); the Educa integration also accepts a JSON number for `valorMensal`/`taxaImplantacao`, converted through its decimal string (never float math). `dispensa` never has a fee — schema 400 + DB CHECK `ck_cliente_prefeitura_dispensa_sem_taxa` (mapped to 400 in PATCH/integration). Old ids `essencial`/`completo` → 400 with a clear message (never silently mapped). Implementation is billed by a `nota_fiscal.tipo = 'implantacao'` note created MANUALLY (never automatic — it would start the atesto clock); competência = emission month; partial unique index `uq_nota_fiscal_implantacao_ativa` (one non-cancelled per client → 409). "Implantação a cobrar" rule: `temImplantacaoACobrar` (single source). MRR excludes implementation; recebido/a receber/inadimplência include it; Painel shows `kpis.implantacao` separately.

**Contract cancellation with notice period (round 12-A).** Pure rules in `lib/cancelamentoContrato.ts` (30-day notice from the date the ofício was RECEIVED; término = pedido + 30; 30-day periods counted from `data_inicio_contrato`; final note = monthly × days ÷ 30 in integer cents, half-up; competência of a period = month it STARTS); transactional writes + audit events in `lib/cancelamentoServico.ts` (`select … for update`, `cliente_evento_contrato`, origem `painel`/`educa`/`sistema`). Migration `0011` adds status `em_aviso_previo` (old CHECK found via catalog) + coherence CHECKs. **The término day is still a contract day**: the cron closes contracts when `término < hoje` (America/Sao_Paulo) and retraction is allowed while `hoje <= término`; the Painel derives the same via `statusContratoNaData` without waiting for the cron. **Closing a contract never cancels debt**: the cron's nota query must NOT filter by `status_contrato` (asserted in unit + integration tests). `criarNota` accepts `ativo`/`em_aviso_previo`, and `encerrado` only for mensalidade when a término exists (final note); mensalidade competência after the last period → 409. Team routes `POST`/`DELETE /api/clientes/[id]/cancelamento` (409 on repeat); Educa route `POST /api/integracao/clientes/[municipioIdExterno]/cancelamento` (idempotent: repeat → 200 `mudou: false`, no new event) shares the auth/rate-limit barrier `lib/autenticacaoIntegracao.ts` with `/api/integracao/clientes`. MRR = ativo + em_aviso_previo; `kpis.avisoPrevio` feeds both Painel and Dashboard.

**Team roles / RBAC (round 15-A).** `equipe_nexaigen.papel` ∈ admin/financeiro/vendas/rh (migration `0012`, existing users = admin). The papel × área matrix lives ONLY in `lib/papeis.ts` (deny by default: unknown area/role → admin only). Every team API route calls `exigirPapel(contexto, area)` (`lib/auth.ts`, replaces bare `exigirSessao`); every `app/(protegido)/<pasta>/layout.tsx` calls `exigirAreaPagina(area)` (`lib/authPagina.ts`: redirects to /login, /trocar-senha or /). Papel is read from the DB on every request (same query as `token_version`), never from the JWT. `PATCH /api/equipe/[id]` (admin only, `lib/equipeServico.ts`) changes papel, bumps `token_version` and revokes sessions; locks admins `for update`; last active admin → 409. **Adding a route**: give it an area and add it to `ROTAS` in `app/api/protecao-rotas.test.ts` — that test reads `app/api/**/route.ts` from disk and fails on any unlisted method, and checks every route × every papel (401/403). Home `/` renders Dashboard for admin/financeiro and `BoasVindas` for vendas/rh.

**New contracts report (round 15-A).** `/contratos` + `GET /api/relatorios/novos-contratos` (area `contratos`). Business rule: contract validity starts at signature ⇒ "new in month" = `data_inicio_contrato` in the month. Pure math in `lib/relatorioContratos.ts` (closed/notice-period counts come from `cliente_evento_contrato`; "MRR da carteira hoje" is `calcularMrr` — same as Painel). **Public map of served municipalities (round 15-B).** Central rule: a client appears ONLY with written authorization (`cliente_prefeitura.autorizacao_divulgacao`, set by hand in the Clientes screen) AND a current contract (`ativo`/`em_aviso_previo` by date — `lib/mapaPublico.ts#elegivelNoMapa`). **Round 16-A3 — test stability, base municipality on leads.**
- **RULE: an integration test that changes STRUCTURE (DDL: alter/drop/add constraint, create/drop table/column/trigger/function, re-running a migration) runs in a THROWAWAY database, never the shared one.** Use `const banco = await vi.hoisted(async () => (await import("@/testes/bancoTemporario")).trocarParaBancoTemporario("x"))` at the top (runs before imports, swaps `DATABASE_URL`), `beforeAll(() => confirmarBancoTemporario(banco, (sql) => query(sql)))`, `afterAll(() => encerrarBancoTemporario(banco))`, and `describe.skipIf(!banco)` on the DDL blocks. DDL takes an ACCESS EXCLUSIVE lock and used to wait 30 s on any other session touching the table. Temp DBs are created like production (no dev seed — nothing liberated).
- Integration setup (`vitest.integration.setup.ts`): `lock_timeout=5s` on every test connection (PGOPTIONS), `application_name=teste:<file>`, a lock/timeout failure prints who waits/blocks (`testes/diagnosticoTravas.ts`), and each file FAILS if it leaves an "idle in transaction" session. `vitest.integration.globalSetup.ts` holds an advisory lock: a SECOND concurrent `npm run test:integration` on the same DB fails immediately (two suites on the shared DB corrupt each other's data).
- Every test with bcrypt, DB or simulated typing gets an EXPLICIT timeout (bcrypt integration tests: 120 s; the login tests no longer depend on each other's state).
- Never `Promise.all` several queries on the SAME transaction client — use `lib/db.ts#consultasJuntas(executor, [...])` (parallel on the pool, sequential on a client; pg@9 drops query queuing).
- Leads in a LIBERATED state must carry `codigo_ibge` from `municipio_base` (server-enforced in `criarLead`/`editarLead` via `municipioDaBase`; name/population come from the base). Legacy leads without code: `POST /api/leads/[id]/municipio` (`vincularMunicipio`, owner or admin, same UF, history line). A lead's municipality is found ONLY by code (entity tags, list filters, export); a lead without code shows "vincular município". The Território status still matches code-less leads by UF + name, on purpose, so a municipality with an unlinked open lead never shows as "não abordado".

**Round 16-A4 — resilient pool, clean suite exit.**
- **RULE: every `pg` Pool AND every long-lived `pg` Client has an `"error"` listener.** An IDLE connection killed by the server (Postgres restart, Railway failover, network drop, 57P01 "terminating connection due to administrator command") emits `"error"`; without a listener Node treats it as an uncaught exception and KILLS THE PROCESS. `lib/db.ts` registers `registrarErroDeConexaoOciosa` (one short log line: error code + message, URLs masked, never data) — the pool drops that client and opens a new one on the next query. Pool options are explicit and commented: `idleTimeoutMillis` 10 s, `connectionTimeoutMillis` 15 s (default is "wait forever"), TCP `keepAlive`. Proven by `lib/db.pool.integration.test.ts`, which runs `testes/sondaPoolOcioso.ts` as a CHILD PROCESS, terminates its idle connection with `pg_terminate_backend` and asserts exit code 0 + a working next query (without the listener the child exits 1). Clients: `scripts/migrate.ts`, `testes/bancoTemporario.ts#ouvirErroDeConexao`, the suite lock, the lock diagnostics.
- **RULE: a test with a throwaway database closes its connections BEFORE the drop** — always `encerrarBancoTemporario(banco, ...ownClients)` (own clients → app pool → drop). `derrubar()` re-checks `pg_stat_activity` for the database, waits up to 3 s for closing sessions, drops anyway and THROWS naming any leftover connection. Never call `banco.derrubar()` directly from a test.
- **RULE: always check the command's EXIT CODE, not just the test count** (`npm run test:integration; echo EXIT=$?`). "Unhandled Errors" make vitest exit 1 even with every test passing.
